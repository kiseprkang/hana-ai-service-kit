# 실습 가이드: "나의 자산 한눈에 보기" 기획을 처음부터 끝까지

> 교육용 가상 과제입니다. 등장하는 고객, 수치, 기능 범위는 모두 가상이며 실제 사내 정책이 아닙니다.

## 0. 이 실습을 처음 하는 분께

- **AI가 대신 기획해 주지 않습니다.** AI는 문서를 정리하고 빈칸을 찾아 주는 도우미입니다. 판단과 최종 확인은 여러분이 합니다.
- **모르는 것은 지어내지 않습니다.** 수치나 법 조항을 모르면 `[확인 필요]`라고 씁니다. 이 실습에서 가장 중요한 원칙입니다.
- **한 번에 한 단계씩 합니다.** 각 단계 끝의 "확인" 질문에 답할 수 있으면 다음 단계로 넘어갑니다.
- **AI 결과는 반드시 읽습니다.** AI가 쓴 문장이라도 입력 자료와 다르면 고쳐야 합니다.

### 처음 보는 용어

자주 나오는 말만 정리했습니다. 더 많은 용어와 약어는 키트 폴더의 `용어_풀이.md`에 있습니다.

| 용어 | 뜻 |
|---|---|
| AI 작업 도구 | 파일을 읽고 쓰며 함께 일하는 AI (Claude Code, Codex) |
| 지시문 | AI에게 "이걸 해 줘"라고 말하는 문장. 이 가이드에는 복사해서 쓸 수 있는 지시문이 있습니다 |
| 명령 창 | 글자로 명령을 입력하는 창. 윈도우에서는 PowerShell을 씁니다 |
| 점검 프로그램 | 명령 한 줄로 실행하는 확인용 프로그램 (`scripts/` 폴더) |
| 산출물 | 과제 정의서, 제품 요구사항 문서처럼 만들어 내는 문서 |
| 1차 출시 | 처음 내보내는 출시. 핵심 기능만 담습니다. 이번 과제의 1차 출시는 "조회 전용"입니다 |
| 2차 출시 | 1차 다음 출시. 아직 정하지 않은 기능(예: AI 추천)을 담을 수 있습니다 |
| 수용 기준 | "이렇게 되면 완성"이라고 말할 수 있는 확인 조건 |
| 검토 관문 | 출시 전에 반드시 통과해야 하는 규제 확인 단계 (G1~G7) |
| 자동 점검 장치 | 파일을 저장하기 직전에 자동으로 확인하는 장치 |
| 규칙·점검 장치 | AI가 지킬 규칙과 자동 점검을 묶은 것. 이 키트 전체를 말합니다 |
| 연결 확인 | 요구사항이 시험 항목까지 빠짐없이 이어졌는지 확인하는 것 |

### 번호 읽는 법

| 표시 | 뜻 |
|---|---|
| REQ-001 | 기능 요구사항 번호 ("이런 기능이 있어야 한다") |
| NFR-001 | 품질 요구사항 번호 (보안, 속도, 기록 같은 조건) |
| AC-001 | 수용 기준 번호 ("이렇게 되면 완성") |
| TC-001 | 시험 항목 번호 (직접 해 보고 확인하는 상황 하나) |
| G1 ~ G7 | 검토 관문 번호 |
| D-001 | 의사결정 번호 |

## 1. 실습 목표

하나의 가상 서비스를 **과제 정의 → 고객 리서치 → 요구·설계 → 검증 → 규제 검토 관문 → 출시 점검 → 출시 후 점검**까지 직접 끝까지 진행합니다. 마지막에는 두 점검 프로그램이 모두 통과하는 것이 목표입니다.

| 얻는 것 | 설명 |
|---|---|
| 문서 체인 | 산출물이 앞 단계에서 뒤 단계로 이어지는 흐름 |
| 기준점 | 무엇을 보고 "통과"라고 할지 정하는 방법 |
| 규제 검토 관문 | 전자금융거래법, 신용정보법·개인정보보호법, 금융소비자보호법, 특금법, 전자금융 보안, 내부통제, AI 거버넌스 |
| 규칙·점검 장치 체험 | 주민번호 형식을 쓰면 자동 점검 장치가 저장을 막는 것 확인 |
| 결정 기록 | 예측과 리뷰일을 함께 남기는 습관 |

> 시간이 부족하면 **필수 경로**만 해도 됩니다: 0 → 2 → 3 → 4 → 6 → 8. 나머지는 시간이 남을 때 합니다.

## 2. 시작 전 준비

### 2-1. 작업 폴더 만들기 (중요)

원본 키트는 그대로 두고 실습용 복사본에서 작업합니다. 폴더 위치는 사람마다 다르므로 **본인 PC에서 키트 폴더가 있는 곳**을 기준으로 합니다.

**방법 A (권장): 탐색기 주소창 활용**
1. 탐색기에서 `hana-ai-service-kit` 폴더를 엽니다.
2. 주소창을 클릭하고 `powershell`을 입력한 뒤 Enter를 누릅니다.
3. 아래 2번 명령부터 실행합니다.

**방법 B: 경로 직접 입력**
1. 아래 1번 명령의 `<키트 폴더 경로>`를 본인 PC의 실제 경로로 바꿔서 실행합니다. (탐색기 주소창에서 복사하면 편합니다)

```powershell
# 1) 키트 폴더로 이동 (방법 B에서만, <...> 부분을 실제 경로로 바꾸세요)
cd "<키트 폴더 경로>"

# 2) 바탕화면에 실습용 복사본 만들기
$desktop = [Environment]::GetFolderPath("Desktop")
$dest = Join-Path $desktop "내_실습_키트"
New-Item -ItemType Directory -Force -Path $dest | Out-Null
Copy-Item -Path ".\*" -Destination $dest -Recurse -Force

# 3) 복사본으로 이동
Set-Location $dest
```

> 💡 `[Environment]::GetFolderPath("Desktop")`을 쓰는 이유: 바탕화면이 OneDrive로 옮겨진 PC에서도 올바른 위치에 복사되도록 하기 위함입니다.

### 2-2. 도구 확인


## 4. 단계별 실습

각 단계에는 **복사해서 쓸 수 있는 지시문**가 있습니다. Claude Code나 Codex 창에 붙여 넣고 결과를 읽은 뒤, 아래 "확인" 질문에 답하세요.

### 단계 0. 과제 정의서 작성 (20분)

**목표:** 무엇을, 왜, 누구를 위해 만드는지 한 장으로 정리합니다.

**할 일**
1. `practice/input/01_기획_메모.md`를 읽습니다.
2. `docs/00_과제정의서.md`를 엽니다.
3. 아래 지시문을 입력합니다.

```text
practice/input/01_기획_메모.md를 읽고 docs/00_과제정의서.md를 채워 줘.
- 배경과 문제, 핵심 성과 지표 2개 이상(측정 방법과 리뷰일 포함), 가설, 포함과 제외 범위를 채워.
- 기획 메모에 없는 수치는 지어내지 말고 [확인 필요]로 둬.
- 규제 영향 표는 G1~G7 각각 '예 / 아니오 / 확인 필요'로 표시하고 근거 한 줄을 적어.
- 다 쓴 뒤 빈칸(확인 필요)을 목록으로 알려 줘.
```

4. AI가 쓴 내용을 읽고 기획 메모와 다른 부분이 없는지 확인합니다.

**확인 질문**
- 제외 범위에 "이체"가 들어 있나요?
- 핵심 성과 지표에 측정 방법이 적혀 있나요?
- 규제 영향 표에서 G2(개인정보)를 "예"로 표시했나요?

> 💡 목표 수치를 모르면 `[확인 필요]`로 두세요. 지어낸 수치는 이 실습에서 가장 큰 감점 요인입니다.

### 단계 1. 고객 리서치 정리 (25분)

**목표:** 인터뷰 다섯 건을 세그먼트와 고객 여정으로 정리합니다.

**지시문**
```text
practice/input/02_인터뷰_요약.md를 읽고 docs/01_고객_리서치.md를 채워 줘.
- 인터뷰 A~E를 묶어서 세그먼트 3개 이상을 만들어. 각 세그먼트에 해당하는 인터뷰 번호를 적어.
- 현재 고객 여정(AS-IS)을 단계별로 정리해. 불편 지점을 반드시 포함해.
- 인사이트 3개를 쓰고, 고객 보호 관점 체크 3항목을 확인해.
```

**확인 질문**
- 고령 고객 세그먼트에 큰 글씨와 단순한 화면이 반영되었나요?
- 가족 계좌 조회에 대한 고객 우려가 인사이트에 적혀 있나요?

### 단계 2. 제품 요구사항 문서 작성 (30분)

**목표:** 제품이 무엇을 하고 무엇을 하지 않는지 명확히 합니다.

**지시문**
```text
docs/00과 docs/01을 바탕으로 docs/02_PRD.md를 채워 줘.
- 제품 한 줄 정의, 목표와 비목표를 써. 비목표에는 이체, 상품 가입, 해지를 넣어.
- 1차 출시(조회 전용)과 2차 출시(AI 추천 검토)로 릴리스를 나눠.
- 금융 규제 요건 표에서 G1~G7 각각을 제품 요구사항 문서에서 어떻게 반영하는지 한 줄씩 써.
- 기획 메모의 '아직 정하지 않은 것'은 미결 사항으로 옮겨.
```

**확인 질문**
- 상품 정보 표시를 1차 출시에 넣었다면 G3(금소법) 항목을 어떻게 다뤘나요?
- 비목표가 1개 이상 있나요?

### 단계 3. 요구사항, 기능 명세, 화면 설계 (40분)

**목표:** 개발팀이 바로 구현할 수 있을 만큼 구체적으로 씁니다. 여기서 만드는 **요구사항 ID와 수용 기준이 다음 단계의 기준점**이 됩니다.

**3-1. 요구사항 (`docs/03_요구사항정의서.md`)**

```text
docs/02_PRD.md를 바탕으로 docs/03_요구사항정의서.md를 채워 줘.
- 기능 요구는 REQ-001부터 번호를 붙여 3개 이상 써.
- 비기능 요구는 NFR-001부터 번호를 붙여 2개 이상 써. 보안(G5)과 감사 로그(G6)를 반드시 포함해.
- 성능 같은 기준값은 모르면 [확인 필요]로 둬.
```

**3-2. 기능 명세 (`docs/04_기능명세서.md`)**

```text
docs/03을 바탕으로 기능 FN-01(자산 요약 조회)과 FN-02(계좌별 잔액 표시)를 docs/04_기능명세서.md에 써 줘.
- 각 기능에 사용자 스토리, 기본 흐름, 예외 흐름(네트워크 오류, 로그인 상태 만료), 데이터 항목을 포함해.
- 수용 기준은 기능마다 3개 이상, 'AC-001'처럼 번호를 붙여서 써. 이 번호는 검증 계획에서 쓸 거야.
- 계좌번호는 마스킹 표시로 쓰고, 로그에 전체 번호가 남지 않는다는 기준을 넣어.
```

**3-3. 화면 설계 (`docs/05_화면설계서.md`, 선택)**

```text
docs/04를 바탕으로 SCR-001(자산 요약) 화면을 docs/05_화면설계서.md에 글로 설계해 줘.
- 안내 문구에 "조회 결과는 참고용이며 실제 잔액과 차이가 있을 수 있다"를 넣어.
- 큰 글씨 옵션을 접근성 항목에 적어.
```

**확인 질문**
- 요구사항에 REQ-, NFR- 번호가 붙어 있나요?
- 수용 기준에 AC- 번호가 붙어 있나요? (다음 단계에서 씁니다)
- 명세서 예외 흐름에 "로그인 상태 만료 후 재인증"이 있나요?

> 💡 이 단계에서 번호를 붙여 두지 않으면 4단계 연결 확인 확인이 불가능합니다.

### 단계 3-1. AI 기능 설계 판단 (10분, 선택)

**목표:** AI가 필요한지 판단하고, 필요 없다면 그 이유를 기록합니다.

1차 출시 범위에는 AI 기능이 없습니다. 따라서 `docs/06_AI기능설계서.md`의 첫 줄에 **"해당 없음"**과 근거를 씁니다.

**지시문**
```text
1차 출시 범위에 AI 기능이 없다는 근거를 docs/06_AI기능설계서.md 첫 줄에 '해당 없음'으로 쓰고, 한 문단으로 설명해 줘.
2차 출시에서 AI 추천을 검토할 때 필요한 항목(모델, 데이터, 평가 기준)만 빈칸으로 남겨 줘.
```

> 💡 AI가 없다는 것도 기록해야 합니다. G7 검토 관문은 이 기록을 보고 판정합니다.

### 단계 4. 기준점과 검증 계획 (25분)

**목표:** "무엇을 보고 합격인지" 기준을 정하고, 그 기준을 시나리오로 확인합니다.

**4-1. 기준점 이해하기**

검증은 다음 순서로 합니다.

1. **기준은 어디서 오는가?** 기능 기준은 04의 수용 기준(AC-), 성능·보안 기준은 03의 비기능 요구(NFR-), 규제 기준은 gates/의 체크리스트, 사업 기준은 00의 핵심 성과 지표입니다.
2. **시나리오는 기준을 확인한다.** 각 시나리오는 "기대 결과"와 "연결 ID"를 가집니다.
3. **빠진 연결을 확인한다.** 모든 REQ, NFR이 시나리오 중 하나에 연결되어야 합니다.

**4-2. 검증 계획 작성 (`docs/08_검증계획.md`)**

```text
docs/08_검증계획.md를 채워 줘.
- 1번 기준점 표: 기능, 성능·보안, 규제, 사업 기준을 각각 어디서 가져왔는지 적어.
- 2번 검증 범위: 기능, 예외, 보안, 규제, 직접 써 보는 테스트를 적어. 보안 기준값은 [확인 필요]로 둬.
- 3번 시나리오: 최소 5개를 쓰고, 각 시나리오의 '연결 ID'에 REQ, NFR, AC, G 중 하나 이상을 적어.
  예: TC-001 잔액 표시 → AC-001, REQ-001
  예: TC-003 로그에 계좌 전체 번호가 남지 않음 → NFR-002, G2
- 모든 REQ, NFR이 시나리오에 최소 한 번 나오도록 해 줘.
```

**4-3. 연결 확인 확인**

```powershell
node scripts\check-traceability.mjs
```

- `[미연결]`이 있으면 그 ID를 시나리오의 연결 ID에 추가합니다.
- 모두 `[연결]`이고 결과가 "모든 요구사항이 검증 계획에 연결되어 있습니다"면 통과입니다.

**확인 질문**
- TC-003을 실제 시험 방법으로 설명할 수 있나요? (예: 로그 파일에서 계좌 패턴 검색)
- 기준값이 [확인 필요]인 항목은 누구에게 언제 확인할지 적었나요?

### 단계 5. 보안 자동 점검 장치 체험 (10분, 선택)

**목표:** 규칙·점검 장치가 개인정보 형식을 막는 것을 직접 확인합니다.

이 단계는 Claude Code 기준입니다. Codex를 쓴다면 교강사의 안내에 따라 같은 내용을 설명으로 확인합니다.

1. Claude Code를 복사본 폴더에서 엽니다.
2. 아래 요청을 그대로 입력합니다.

```text
practice/테스트_메모.md 파일을 만들고 다음 내용을 써 줘: "테스트 고객 주민번호 900101-1234567"
```

3. 자동 점검 장치가 **"저장이 차단되었습니다"** 메시지를 보이면 성공입니다.
4. 같은 요청을 다시 하되, 번호를 `900101-1******`로 마스킹해서 요청합니다. 이번에는 저장됩니다.
5. 실습이 끝나면 `practice/테스트_메모.md`를 삭제합니다.

**확인 질문**

> ⚠️ 실제 고객 번호는 어떤 실습에서도 입력하지 않습니다.

### 단계 6. 규제 검토 관문 7종 판정 (40분)

**목표:** 규제 요건을 체크리스트로 확인하고 판정합니다.

**지시문 (검토 관문별로 한 번씩 사용)**
```text
gates/G2_개인신용정보_개인정보.md를 열어서 체크리스트를 docs 산출물과 대조해 줘.
- 근거가 있는 항목은 [x]로 표시하고, 근거가 있는 문서와 위치를 옆에 적어.
- 근거가 없는 항목은 [ ]로 두고 '무엇이 필요한지'를 한 줄로 써 줘.
- 판정은 아직 바꾸지 마. 판정 후보(통과, 조건부 통과, 보류)와 이유만 알려 줘.
```

AI가 제안한 판정 후보를 읽고, 여러분이 최종 판정을 `**판정:**` 줄에 적습니다.

**판정 값**
- `통과`: 모든 항목 근거가 있음
- `조건부 통과`: 보완 조건이 있음 (조건과 기한을 "조건과 보완 사항"에 적습니다)
- `보류`: 해결되지 않은 문제가 있음
- `해당 없음`: 이번 과제와 무관함 (근거 필수)

> ⚠️ `**판정:**` 줄을 지우지 말고 값만 바꿉니다. 점검 프로그램이 이 줄을 읽습니다.

**검토 관문별 힌트 (이번 과제 기준)**

| 검토 관문 | 이번 과제의 핵심 쟁점 | 예상 판정 |
|---|---|---|
| G1 전자금융거래법 | 조회 전용이라 거래 조건은 해당 없음 (단, 오류 정정 안내 필요) | 조건부 통과 가능 |
| G2 개인신용정보·개인정보 | 잔액, 계좌번호 표시, 로그 마스킹, 가족 계좌 동의 | 보완 후 통과 |

| G4 특금법 | 거래 기능이 없어 해당 없음 (근거 필수) | 해당 없음 |

> ⚠️ 법령 조항은 최신 원문을 확인하기 전까지 `[확인 필요]`로 둡니다. AI가 조문을 인용하면 원문 확인 여부를 꼭 물어보세요.

**확인 질문**

## 7. 자주 나는 문제 (FAQ)

**Q1. `node` 명령이 인식되지 않아요.**
Node.js를 설치한 뒤 윈도우 명령 창(PowerShell)을 다시 열어 주세요. `node -v`로 확인합니다.

**Q2. `check-gates`에서 판정 줄을 못 찾는다고 나와요.**
검토 관문 파일의 `**판정:**` 줄이 그대로 있는지 확인하세요. 줄을 지우지 말고 값만 바꿉니다.

**Q3. `check-traceability`가 계속 미연결이라고 나와요.**
08 검증 계획의 시나리오 표 안에 REQ-001 같은 ID가 그대로 적혀 있는지 확인하세요. 오타(예: REQ-1)가 있으면 03과 같은 형식(세 자리 숫자)으로 맞춥니다.

**Q4. 자동 점검 장치가 계속 저장을 막아요.**
주민등록번호나 카드번호 형식이 문서에 들어 있는지 확인하세요. 마스킹하면 통과합니다.

**Q5. AI가 법 조항을 인용했어요. 믿어도 되나요?**
원문을 확인하기 전까지는 `[확인 필요]`로 두세요. AI는 조문을 틀리게 인용할 수 있습니다.

**Q6. AI가 시키는 대로 했는데 결과가 이상해요.**
한 번에 한 문서씩 요청했는지 확인하세요. 그래도 이상하면 "이 부분의 근거가 어느 입력 자료에 있는지 알려 줘"라고 물어보세요.

**Q7. 원본 키트를 실수로 고쳤어요.**
교강사가 배포한 원본 폴더는 그대로 두고, 단계 2-1의 복사본을 다시 만들어 사용하세요.
